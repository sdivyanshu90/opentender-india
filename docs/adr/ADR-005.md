# ADR-005: Dataset Storage

**Status:** Accepted (amended 2026-10-04)

## Context
One giant JSON file would make diffs unreviewable and frontend loads slow (§44).

## Decision
Hot storage = per-tender gzip JSON at `data/hot/<prefix>/<canonical_id>.json.gz` plus `data/state.json` (revision/hash/status index used for cross-run diffing). Frontend payloads = slimmed shards under `data/indexes/` with a manifest. Source documents are never committed - metadata, hashes and extracted text only.

## Consequences
Git history stays reviewable; corruption affects single records; exports regenerate deterministically.

## Amended 2026-10-04

The original decision above is kept for history. Its storage layout (per-tender
gzip JSON plus `data/state.json`) is unchanged; what changed is where it lives
between runs.

**Change.** `data/hot/`, `data/state.json`, `data/index/` and `data/indexes/`
are no longer committed (see `.gitignore`).

- `fetch-tenders` carries the store (`data/hot`, `data/state.json`,
  `data/indexes/search-docs.meta.json`, `data/ai-cache`) between runs in the
  GitHub Actions cache (`tender-store-<run_id>`, restored by prefix).
- The built datasets (`search-docs.json.gz`, its meta file, the manifest and
  `status/sources.json`) go to `deploy.yml` as the `site-data` artifact
  (14-day retention). `deploy` runs on push to `main` and after
  `fetch-tenders`/`weekly-reconcile` complete, downloads the newest artifact
  and publishes it with the frontend.
- Still committed: `status/` and `data/ai-queue.jsonl` (small), and
  `archive/` - immutable monthly partitions written by `opentender archive`
  (`<source>_<YYYY>_<MM>.json.gz`, merged by `canonical_id`, never overwritten).
- Jobs that touch the store or push to `main` (`fetch-tenders`,
  `source-health`, `archive`) share the `data-commit` concurrency group.

**Rationale.**

- Repository growth: with organisation-walk ingestion a run touches roughly
  25k tenders (24,651 advertised on 2026-10-04). Committing rewritten files
  daily grows the pack history without bound.
- Noise: those commits bury reviewable changes (code, config, status) under
  data churn.
- Nothing is lost by dropping git as the primary store: every run re-walks all
  active tenders, and long-closed ones are preserved in `archive/`.

**Consequences.**

- An evicted or missing cache loses revision history (corrigendum diffs,
  `first_seen`) accumulated so far, not current tender data.
- Git history is no longer a record of daily dataset state; the dataset on the
  site is only as old as the newest successful ingestion artifact.
- `build-index` has a quality gate (empty index, or a drop of more than 50%
  versus the previous build, exits 4), so a bad run cannot replace a good
  published dataset; the previous count is read from the cached meta file.
